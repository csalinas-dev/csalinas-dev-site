# csalinas.dev — Claude Code Guide

## Project Overview

Next.js 15 (App Router) personal portfolio site for Christopher Salinas Jr. Includes blog posts, games, and other pages. The main game is **Wordleverse**, a Wordle clone with user auth and gameplay history.

## Tech Stack

- **Framework**: Next.js 15 + React 19 (App Router; codebase is primarily `.js`/`.jsx`, with TypeScript included as a devDependency)
- **UI**: Material-UI (MUI) v6 + Emotion
- **Auth**: NextAuth v4 (JWT sessions, credentials + OAuth)
- **ORM**: Prisma with MySQL
- **Email**: Nodemailer (SMTP)
- **State**: React Context + Reducer

## Key Path Aliases (jsconfig.json)

- `@/` → `src/`
- `@wordleverse/*` → `src/app/(pages)/games/wordleverse/(game)/*`
- `@wordleverse-history/*` → `src/app/(pages)/games/wordleverse/history/*`

## Important Patterns

- Server actions live in `_actions/` directories and begin with `"use server"`
- Client components that need server data call server actions directly (Next.js handles the RPC boundary)
- `sendVerificationEmail` lives in `src/lib/auth.js` — do not duplicate it elsewhere
- `getCurrentUser()` in `src/lib/auth.js` looks up the authenticated user by email from the session; all server actions use this to get `userId`
- `/blog` is the site's writing — project write-ups **and** general technology posts. Every post is a directory: `src/content/posts/<slug>/index.mdx`, with its images beside it. `export const meta` is the front matter (`title`, `description`, `date` as `YYYY-MM-DD`, `category`, `cover` required; `hero`, `tags`, `link`, `linkLabel` optional) and `export default` is the body. `meta` never carries a slug — the directory name is the slug and the URL.
- `src/content/posts/index.js` is the hand-maintained registry of the **MDX** posts. Adding a post is a directory, one `import` line there, **and its slug in `src/content/posts/slugs.js`** — the registry throws at import if those two drift, because an unreserved slug is one the Substack sync could take. It is a list rather than an `fs` glob so posts are build-time ESM imports: no runtime markdown compilation, and a bad `meta` throws during `npm run build` instead of at request time. The routes do not import it; they import `@/lib/blog`.
- **`src/lib/blog/` is the blog's data layer and the only post source `/blog` and `/blog/[slug]` import.** It merges the MDX registry with the `SubstackPost` rows into one shape (`{ source, slug, title, description, date, publishedAt, category, cover, tags }`, plus `hero`/`readingTime`/`link`/`Content`/`contentHtml` in full), so neither route knows where a post came from. Exactly one of `Content` and `contentHtml` is non-null. `shape.js`, `headings.js` and `reading-time.mjs` are pure — no Prisma, no `.mdx`, no `@/` alias — which is what lets `.agent/scripts/verify-blog-posts.mjs` exercise the merge with no database. Full contract in `src/lib/blog/README.md`.
- **An MDX post always owns its slug.** The slugs in `src/content/posts/` are reserved names in the `/blog/<slug>` namespace. The Substack sync will never assign one — it skips a reserved candidate exactly as it skips a taken one and moves on to `-2`, `-3`… And if a row somehow already holds a reserved slug (it predates this rule, or an MDX post was added afterwards), the read layer resolves that URL to the MDX post and drops the synced row from every listing, logging its slug once so the shadowing is visible in the server log. The remedy for a shadowed row is operator-level: rename the MDX directory, or delete the row. MDX wins because those URLs are already public, already linked, and already the target of the permanent `/projects/:slug` redirect. Enforced at **both** ends (`freeSlug` in `sync.js`, `mergePosts` in `shape.js`) because one alone leaves a race. `sync.js` reaches `slugs.js` by a **relative** import — the `@/` alias does not resolve under the plain-node hook that keeps the verify scripts runnable offline, and the failure looks like a missing module rather than a wrong import style.
- **Both blog routes are `force-dynamic`**, for the same reason `wordleverse/leaderboard/page.js` is: they query MySQL and the Docker image runs `next build` *before* the deploy runs `prisma db push`. So `generateStaticParams` and `dynamicParams = false` are gone from `[slug]/page.jsx` — a synced post that arrives between deploys has to be reachable without a rebuild. Nothing in the blog may touch the database at build time; `DATABASE_URL="mysql://u:p@127.0.0.1:1/none" npm run build` is the check. There is deliberately no `unstable_cache` and no `revalidate`: a stale listing right after a sync is a worse first bug than one small query per request.
- **MDX posts never touch the database.** `getPost` resolves the registry first and returns without querying, and `getPosts` degrades to MDX-only when the store throws (logging the error's *code*, never its `message` — a driver may echo back the values it was handed and one of those is an article body). So `/blog` and `/blog/hashtag` still render with MySQL down.
- **The blog has exactly one `dangerouslySetInnerHTML`**, in `[slug]/page.jsx`, and it goes on `<Article>` **itself, never a wrapper `<div>`** — the drop cap is `> p:first-of-type::first-letter` in `[slug]/components.jsx`, a direct-child selector, so a wrapper silently kills it and the only symptom is a missing large first letter on synced posts. The HTML it is fed is the artefact `src/lib/substack/sanitize.js` already produced: no second sanitization pass and no filtering at render time. If something renders badly because a tag was dropped, change the allowlist there — the content hash is taken after sanitizing, so that re-syncs every post automatically.
- Heading ids for synced posts come from `withHeadingIds` in `src/lib/blog/headings.js`, applied in `fromSyncedRow` rather than in a component: `Heading2` in `src/mdx-components.js` is a React component and never runs over injected HTML, and `PostBody.jsx` uses the id as both the anchor and the React **key** — so a synced post without ids is a TOC of dead `#` links with duplicate keys. The slugifier (`slugifyHeading`) is shared with `mdx-components.js` so the same heading text anchors identically whatever the source.
- Remote covers and heroes (synced posts) render as a plain `<img>`, deliberately **not** `next/image`: an optimized remote image needs its host in `next.config.mjs`'s `remotePatterns`, and a Substack CDN hostname missing from that list is a hard render failure caused by third-party data. `cover`/`hero` is a `StaticImageData` object for MDX and a URL string for synced; components branch on `typeof`. `Hero` and `RemoteHero` in `[slug]/components.jsx` share one CSS constant so they cannot drift.
- Post images are static ESM imports (`import cover from "./cover.jpg"`), which is why `meta.cover` is an object with `src`/`width`/`height`/`blurDataURL` rather than a URL string — hand it straight to `next/image` and `placeholder="blur"` works. Keep committed images under ~500 kB.
- `@next/mdx` is pinned to **15.x** to match `next@15`; the 16.x on npm targets Next 16. `pageExtensions` in `next.config.mjs` includes `"mdx"` **for aliasing, not routing** — Next only applies its vendored React aliases to files matching `codeCondition.test` (js/jsx/ts/tsx/cjs/mjs) *or* `pageExtensions`, so without it a `.mdx` module in the RSC layer resolves the client `react/jsx-dev-runtime` against the react-server `react` and every post 500s in dev with `Cannot read properties of undefined (reading 'recentlyCreatedOwnerStacks')`. It creates no routes: posts live in `src/content/`, and only `page`/`layout`/`route` files are routed out of `src/app/`. Do not remove it.
- `src/mdx-components.js` must stay a **server** module (no `"use client"`) and overrides exactly three things: `code` (fenced blocks only), `a` (internal hrefs through `@/components`' `Link`, external ones `target="_blank"`), and `Image` (so a post body can use `<Image src={shot} />` without importing it).
- `FormattedDate` formats in the *runtime's* timezone, so a bare `YYYY-MM-DD` (parsed as UTC midnight) renders a day early anywhere west of Greenwich. The blog pages pass `new Date(date + "T00:00:00")`, the same thing the Wordleverse header does.
- Code highlighting is `sugar-high`, themed entirely through the `--sh-*` variables in `globals.css` — there is no highlighter theme file and no build-time syntax plugin. The `code` override calls `highlight()` and sets `dangerouslySetInnerHTML`; that is safe only because the input is repo-authored MDX compiled at build time.
- Hygraph is **still** used, by `/games/mini-motorways` only. `src/lib/hygraph.js`, the `graphql`/`graphql-request` deps, and the `media.graphassets.com` remote pattern in `next.config.mjs` all stay — that page is unlinked from the nav, so breaking it is easy to miss.
- `/projects` and `/projects/:slug` are permanent redirects to `/blog` and `/blog/:slug`; the three migrated posts kept their slugs.
- The GitHub profile card is served from `src/app/api/github/card`. It renders the whole profile (hero intro + streak + stats/languages) as one themed SVG (VS Code palette) via `src/lib/github/{api,svg,palette}.js`. Consumed by the `csalinas-dev/csalinas-dev` profile repo as `<img src="https://csalinas.dev/api/github/card?key=...">`.
- The same card is embedded on this site's `/github` page as `<img src="/api/github/card">` (no key — the route allows same-origin requests).
- The card route is gated: requests must come from GitHub's Camo image proxy (`github-camo` User-Agent — README `<img>`s are proxied, never fetched by the viewer's browser, so there is no `Referer` to match on) **and** carry the `GITHUB_CARD_KEY` secret as `?key=`. Same-origin requests (the `/github` page) bypass both checks via `Sec-Fetch-Site`, falling back to a `Referer` host match. It is rate-limited in-memory (`src/lib/rate-limit.js`, 30 req/min/IP by default). Upstream GitHub GraphQL results are memoized with `unstable_cache` (60s) in `src/lib/github/api.js` (`getOverview`/`getStreak`) so the PAT is called at most once/minute regardless of request volume — this is what keeps `GITHUB_STATS_TOKEN` from being rate-limited. The route's response `Cache-Control` (consumed by GitHub's Camo proxy) is also 60s, so the rendered streak/stats stay near-live (subject to Camo's own internal minimum cache TTL).
- The card SVG must not use CSS animations that start from `opacity: 0`. It is displayed inside an `<img>` (both on `/github` and on the README), and Chrome rasterizes an SVG image at animation time 0 without advancing it — a fade-in leaves the animated content permanently invisible.
- The `/games` index is data-driven: `src/app/(pages)/games/games.js` is the manifest (`{ slug, title, href, Artwork }` per game, in display order) and `page.jsx` is one `.map` over it. Every tile is the same `GameCard` from `_components/GameCard.jsx` — the **card** owns the portrait `1 / 2` aspect ratio, the chrome and the title overlay, so an artwork never sets its own shape; artwork is authored as a square `viewBox="0 0 300 300"` (or an `<Image fill>`) in one module per game under `_artwork/`. The grid is a single `repeat(auto-fit, minmax(min(9rem, 100%), 1fr))` rule and the title is sized in container query units off the card, so adding a game means adding a manifest entry and an artwork file and touching no CSS.
- `/games/tic-tac-overflow` is a two-player tic-tac-toe variant in `src/app/(pages)/games/tic-tac-overflow/`. Each player keeps at most three marks (`MAX_MARKS`); placing a fourth clears **that player's** oldest one, tracked as a per-player queue in `state.history`. `TicTacOverflow.jsx` is the mode picker: **same device** is the original hotseat game (its own `useReducer`, zero network calls — the realtime core is not in that branch at all) and **online** is the same board driven by a room. `?room=CODE` deep-links into a room; the effect that reads it runs after mount because the page is prerendered.
- Both modes fill the *same* `context/index.jsx` Context — `{ state, dispatch, canPlay, canReset, online }` — so Cell, Status, Toolbar and Play Again are shared verbatim. `OnlineGame.jsx` fills it from `useRoom` instead of `useReducer` and translates the existing action creators into `send()`. `online` is null hotseat and carries the per-player view (your mark, opponent, room code, connection) when networked; `canPlay` closes the board on the opponent's turn and `canReset` makes "play again" a post-win rematch rather than a mid-game wipe.
- The multiplayer definition is `multiplayer.js` (id `tto`), registered in `src/lib/realtime/registry.js`. It **calls** the hotseat `placeMark` reducer rather than restating the expiry rule — one implementation, server-authoritative. It is named `multiplayer.js` and not the `game.js` the core's README suggests because `Game.jsx` sits beside it and webpack treats two modules differing only in case as a collision on Windows/macOS. Its `createState`/`PLAY AGAIN` go through `createBoard(first)`, which is also what seeds hotseat `defaultState` — and `PLAY AGAIN` passes the winner, which is how the winner opens the next game online while hotseat always opens with X.
- Online state deliberately omits `showExpiring`: the hint is a per-player display preference in `localStorage` (`TICTACOVERFLOW-PREVIEW`), merged into the context state client-side, so one player turning it off can never change what the other sees or how the rule runs.
- MySQL JSON columns do **not** preserve object key order, so nothing in a room's `state` may depend on it. TTO is safe because `board` and `history.X`/`history.O` are arrays (order intact) and `history` is only ever read by key; the turn is a mark string and a seat is `player.slot`, an integer.
- That hint (fading the mark the next move clears) is toggleable. `getExpiringCell` always reports the rule; `getPreviewedCell` is the display-level wrapper that returns `null` when the player has the hint off — read the latter in components, never the former, so turning the hint off can never alter play. The preference is restored in an effect after mount rather than seeding `defaultState`, because the page is prerendered and the first client render has to match the server's markup.
- `/games/edge-case` ("Edge Case" — Dots and Boxes) keeps **all** of its rules in `src/app/(pages)/games/edge-case/_lib/`. That module is pure, synchronous and dependency-free so the server and every client run it unchanged: `createState`, `drawEdge(state, { orientation, index }, slot) => { state, error? }`, `getResult` (ties are reported as ties, never broken), `reducer(state, action, player)` for the shared realtime core, plus the edge/box indexing helpers. The coordinate convention for `state.edges` and `state.owners` is documented at the top of `_lib/edges.js` — read it there rather than re-deriving it, and never re-implement a rule in a component.
- Edge Case's online half is `multiplayer.js` (id `edge-case`, registered in `src/lib/realtime/registry.js`) plus `online/`. The room's state wraps the engine — `{ phase: "lobby" | "playing", size, slots, game }` — so a room exists *before* a board does: `_lib/createState` needs two to four slots, and a lobby has neither. `slots` is an array in join order, maintained by `onPlayersChanged` (the reducer is only handed the one player who acted, never the roster), and it becomes the engine's turn order at `START`. `status` returns "lobby" until the host starts, which is what holds the door open for late arrivals and then shuts it — the core turns a newcomer away once status leaves "lobby", and `useRoom` degrades them to spectating.
- Only seat 0 (`HOST_SLOT`, the creator — nobody ever vacates a seat) may `SET SIZE` or `START`. Nothing can infer when everybody has arrived, so the host says so.
- Names and colours are seat data, not game state: they live on `GameRoom.players[]` and are edited by re-POSTing `/api/rooms/[code]/join` (`online/seat.js`), which the core allows while the room is in "lobby". That is what makes a colour lock live for everyone — `assignColor` refuses a colour someone holds and silently hands out a free one instead, so the UI must render the snapshot that comes back, never the colour it asked for. `createPlayers(slots, { names, colors })` in `players.js` turns those seats into the board's cast; `PLAYER_PALETTE[].choice` ("blue"/"purple"/"orange"/"green") is the wire name and `.color` the CSS variable.
- `Game.jsx` is shared by the hotseat game and the room. The context value carries `online`, null on one device and the per-player view otherwise, and `Game` reads exactly two things off it: `youSlot` (the seat this browser holds, resolved by the server from its token) and `interactive` (`youSlot === game.turn && !finished`). The turn banner names `game.turn`, never `youSlot` — online those are usually different people. Spectators are the same board with `interactive={false}`.
- `src/lib/qr.js` is a from-scratch QR encoder (byte mode, ECC level M, versions 1-10) used by the spectator view's join code. It exists because an image service is a third-party request from a page that makes none and would leak the room code; it is deliberately not a vendored library because encoding one short URL does not need four ECC levels and forty versions. The two arrays at the top are the only numbers the spec does not let you derive — everything else (module count, alignment positions, BCH format/version bits) is computed. Verified by decoding the rendered SVG back to its payload with an independently written reader.
- `/games/race-condition` ("Race Condition" — the site's Orbito) keeps **all** of its rules in `src/app/(pages)/games/race-condition/_lib/`, the same way Edge Case and Connect 404 do: pure, synchronous, dependency-free, importing nothing but its own siblings, so the server and every client run it unchanged. No rule may be restated in a component or in the realtime core. A turn is **one atomic `PLAY TURN` action** — `playTurn(state, { move, place }, slot)` runs slide → place → orbit in a single call, which is what structurally guarantees the rulebook's "only after pressing the Orbito-button can a valid 4-in-a-row be created": no state exists in which a marble has landed and the button has not.
- Step 1 of a Race Condition turn moves **one of your OPPONENT'S marbles**, never your own ("Once placed, you cannot move your own marbles anymore. Only your opponent can!"), orthogonally only, onto an empty square, and it is optional. This is the rule the game is most often misremembered as not having; reaching for your own marble is refused with `MoveError.OwnMarble`.
- Both of Race Condition's orbits — the 12 border squares and the 4 centre squares — turn **counter-clockwise** one position per press, and empty squares travel too (a press is a permutation of all 16 cells). The indexing/adjacency convention is documented at the top of `_lib/board.js` and the two orbit tracks at the top of `_lib/orbit.js`; read them there rather than re-deriving them, because a renderer that turns the board the other way still plays a legal-looking game. Both tracks and the ten winning lines are derived in code and asserted against verified literals rather than pasted in.
- Filling the Race Condition board with no line runs the 5 overtime presses **inside the same `playTurn` call** — nobody chooses anything during them, so the outcome is decided the instant the sixteenth marble lands, and a separate action would let one disconnect freeze a finished game. `lastTurn.spins` (1 normally, 2…6 in overtime) plus `lastTurn.cellsBeforeOrbit` is the whole animation contract. Ties are reported as ties: `drawReason` is `"simultaneous"` (both colours on one press, `winningLines` carries both) or `"exhausted"`.
- `node .agent/scripts/verify-race-condition.mjs` is how the Race Condition engine is checked — this repo has no test runner, so the checks are a committed script. It re-derives the orbit tracks and lines, pins the press direction to an explicit destination table, walks a full 12-press cycle, cross-checks the win scan against a second scanner written from scratch inside the script, and self-plays 2000 games. It runs under bare `node` via `.agent/scripts/lib/esm-resolver.mjs`, a generic resolve hook that retries extensionless relative imports — reuse that hook for the next engine's script rather than writing another.
- Font Awesome runs as a kit `<Script>` that replaces `<i>` elements with `<svg>` in the DOM. Any `<i>` React might later unmount (a conditionally rendered icon) must sit inside a wrapper element React owns, or the unmount throws `NotFoundError: Failed to execute 'removeChild'`.
- `src/lib/realtime/` is the shared multiplayer core for every networked game (`/api/rooms/*`, `useRoom()`, the `GameRoom` Prisma model). It is deliberately game-agnostic: a game plugs in a pure `{ id, maxPlayers, colors, createState, reducer }` definition registered in `src/lib/realtime/registry.js`, and **no game rules ever live under `src/lib/realtime/`**. Identity is one `crypto.randomUUID()` per browser in `localStorage` under `CSALINAS-PLAYER-TOKEN`; that token *is* the authorization (the server resolves which seat sent it — request bodies never name a slot), which is also what makes rejoin-after-disconnect free. **It never appears in a URL** — POST bodies carry it, the snapshot route reads an `X-Player-Token` header, and the SSE stream (where `EventSource` cannot set headers) takes a single-use ~30s ticket from `src/lib/realtime/tickets.js` instead, so nothing that reaches a proxy access log can be replayed. Tokens are stripped in exactly one place (`publicPlayer` in `players.js`, called only by `roomPayload` in `serialize.js`) — never serialize a raw `GameRoom` row. Mutations are optimistically concurrent: an action carries the revision the client last saw and the write is a conditional `UPDATE ... WHERE revision = ?`, so a loser gets 410/409/422 with the authoritative room attached. Rooms expire 60 minutes after their last accepted action and answer **410 Gone** thereafter. Full contract in `src/lib/realtime/README.md`.
- Two independent facts say somebody is not at the table, and they are never interchangeable: `player.left` (deliberate — they gave up the seat, or the host removed them) and `player.connected` (a stream, snapshot, join or move has been heard from them inside `PRESENCE_STALE_MS`). `src/lib/realtime/absence.js` is the one place that reads them and the one place their wording lives; components call `absenceOf`/`absenceTag`/`absenceSentence` rather than testing the flags, so a dropped phone never gets a disconnected player's sentence. Presence is in-memory (`presence.js`) rather than on the row, which has a consequence: it does **not** move the revision, so the watcher cannot notice it — `subscribeRoom` runs its own `PRESENCE_POLL_MS` timer that both re-asserts this stream's own presence and re-publishes the payload when the room's roster of live tokens changes. Without that timer a quiet lobby counts everybody out at 45s and a real disconnect never reaches a single screen.
- Leaving is `POST /api/rooms/[code]/leave` (`useRoom().leave(slot?)`). Omit `slot` for your own seat; pass one to remove somebody else, which is host-only and lobby-only and enforced on the server whatever the UI shows. In the lobby the seat is deleted; mid-game it stays (the board and turn order still have to make sense) and is flagged `left`. `useRoom` also fires a `sendBeacon` leave on `pagehide` — which fires on a *reload* as well as a closed tab, so `joinRoom` clears `left` on rejoin; without that a refresh would tell the room you had walked out.
- Schema changes reach production through the `Apply Prisma schema` step in `.github/workflows/deploy.yml` (`docker compose build` → `db push --skip-generate` → `up -d`). It intentionally omits `--accept-data-loss` so a destructive change fails the deploy instead of dropping a table.
- `src/lib/github/font.js` embeds the Sono latin variable woff2 as a base64 data URI; `svg.js` injects it as an `@font-face` so cards render in Sono inside GitHub's `<img>` sandbox (external fonts can't load there). Regenerate by re-downloading the latin woff2 from the Google Fonts css2 API and base64-encoding it.
- `/blog/[slug]` is an editorial two-column shell (metadata rail + split title, hero, sticky heading TOC + 68ch article, prev/next footer) and it stays a **server** component — now `force-dynamic` rather than prerendered, per the bullet above. Every part of the shell that a synced post can lack (category, description, hero, tags, the external link) renders conditionally; nothing shows a placeholder. The only client parts of a post are `[slug]/PostBody.jsx` and `src/components/CopyButton.jsx`. `[slug]/components.jsx` is still a `"use client"` module of Emotion primitives the server page imports — that is the repo's existing pattern, not a boundary. **`src/mdx-components.js` must never get `"use client"`** (the comment at its top says why); it may *import* client components, which is how `CopyButton` reaches a code block.
- **`document.body` is the scroll container, not the window** — `globals.css` sets `body { height: 100svh; overflow-y: auto }`. So `window.scrollY` is permanently `0` and `scroll` never fires on `window`. `PostBody.jsx` listens on `document.body` and computes progress purely from the article's `getBoundingClientRect()`, which needs no scroll-container arithmetic at all. Anything else that reacts to scrolling must do the same.
- **Full-viewport-height budgets on this site are written in `svh`, never `vh`.** `vh` is the *large* viewport — the height the page would have with a mobile browser's chrome retracted — so `100vh` is taller than the screen whenever that chrome is showing (~86px on an iPhone 16 Pro Max), which put a phantom scroll on every page. `svh` is never taller than what the user can see. `svh` was chosen over `dvh` so that a toolbar retraction can never resize a game board mid-play: `hashtag/Game.jsx` and `wordleverse/(game)/Game.jsx` size a whole playfield off the viewport, and `dvh` is a moving target. The trade is that when the chrome retracts, `body` stays short and the uncovered strip at the bottom is painted by `html`'s `background-color` (`globals.css:56`), the same flat colour — so it cannot be seen. This applies only to declarations asserting or budgeting against the *full* screen height; fractional `vh` (a `25vh` toast offset, a `75vh` max-height) is left alone.
- Everything measured off a rendered post lives in `PostBody.jsx` and nowhere else: the h2 list, the active entry, and the `LONG_POST_SCREENS = 2` rule that decides whether a post is long enough to earn a progress bar and a TOC. All of it is filled in from an effect so the first client render matches the prerendered HTML, which carries neither. Consequence worth knowing before calling it broken: **the three current posts are 422-499 words, so at a normal desktop viewport none of them shows either affordance** — that is the rule working. `goldwater-bank` has zero `##` headings and therefore never gets a TOC at any size.
- The TOC is read back out of the rendered DOM (`article.querySelectorAll("h2")`), so heading ids have exactly one generator: the `h2` component in `src/mdx-components.js`. Deriving the TOC on the server would need a second slugifier that has to agree character for character. That component **preserves an incoming `id`** — remark-gfm's footnotes section arrives as `<h2 id="footnote-label">` and is filtered out of the TOC by `closest("[data-footnotes]")`.
- Read time is injected at build time by `remarkReadingTime` in `src/lib/mdx/remark.mjs` (wired in `next.config.mjs`), which pushes an `export const readingTime` onto each compiled post; `remarkCodeMeta` in the same file forwards a fence's meta string through `hProperties` so ```` ```ts title="x.ts" ```` reaches the `pre` component. Neither adds a dependency. `src/content/posts/index.js` throws at build if `readingTime` is missing, so a misregistered plugin fails the build instead of shipping a blank rail. The **200 wpm constant and the rounding live in `src/lib/blog/reading-time.mjs`**, shared with `readingTimeFromHtml`, which counts a synced post's stored HTML at render time — both exclude code, or two posts of the same length would report different numbers. That file is `.mjs` because `next.config.mjs` loads `remark.mjs` under plain Node.
- `.agent/scripts/shot.mjs` drives headless Chrome over raw CDP (no puppeteer, no deps) to screenshot or measure a running `next start`. `node .agent/scripts/shot.mjs <url> <width> <out.png|-> [evalFile.js]`; **every** run prints `{"viewport":{w,h,requested},"result":<the eval file's last expression>}` on stdout, which is how visual changes get measured rather than eyeballed. A bad argument exits **2** before Chrome is spawned and a CDP error or failed navigation exits **1**, so the tool never reports numbers for a viewport nobody asked for. `viewport.w`/`h` are read back out of the page (`innerWidth`/`innerHeight`) *after* navigation and **that is the number to trust, not the width you asked for**: `mobile` emulation is on below 900px, and under it a page with no `<meta name="viewport">` lays out at 980px however wide you asked — that run warns on stderr and still exits 0, because it is Chrome behaving correctly rather than an error. Never run `next dev` against a worktree a `next start` is serving — it clobbers `.next` under the running server.
- `src/lib/substack/` ingests the Substack RSS feed into the `SubstackPost` model. Full contract in `src/lib/substack/README.md`; the rules that bite are these. **RSS field names stop at `feed.js`** — `content:encoded`, `dc:creator`, `enclosure`, `pubDate`, `guid` and the `@_` attribute prefix appear there and nowhere else in `src/`, and the verify script greps for them. Everything downstream sees a source-neutral shape (`id`, `published`, `mediaUrl`…). **`sanitize.js` is a security boundary**: the floor is `sanitize-html@^2.17.7` because five sanitizer bypasses were fixed in that package during 2026 — and its standalone GitHub repo reads "archived" with a popular issue calling it abandoned, both of which are **stale**; it moved into the ApostropheCMS monorepo and ships monthly, so check npm before swapping it. Two traps live in that config: `allowedAttributes` is applied *after* `transformTags`, so `rel`/`target` added by a transform are silently stripped unless also allowlisted; and a relative `href`/`src` carries no scheme, so scheme checking never fires and it resolves against `csalinas.dev` once rendered. **The allowlist is therefore data, not code**: `ELEMENTS` declares each surviving element once, `allowedAttributes` *and* the URL-policing `transformTags` are derived from it, and `auditAllowlist()` runs at import time so allowlisting a name in `URL_BEARING` as a plain attribute is a boot failure rather than a quietly weaker sanitizer. That shape exists because hand-written transforms shipped the hole it closes — `<source>` was allowlisted with `srcset` while the absolute check lived in the `img` transform, and inside `<picture>` the browser prefers the `<source>`, so a relative `srcset` became a same-origin `GET` on a third party's chosen path with `imagesDropped` still reporting `0`. A `srcset` is **never split on `,`** — per the HTML spec a candidate URL is a run of non-whitespace characters, and Substack's CDN puts comma-separated transform parameters *inside* the path (59 of 67 `src` values on the live astralcodexten feed contain one), so splitting on the comma rejected every real `<source>` and reported them as dropped images; the validator calls `parse-srcset`, which is the same parser sanitize-html itself runs on that attribute. A failed required URL drops the element through **`exclusiveFilter`, never by renaming the tag** — that is a deliberate workaround for an upstream bug (`sanitize-html/index.js:667-681`: the `skip` branch returns before `delete transformMap[depth]`, so a renamed-then-discarded element rewrites the *next* closing tag at that depth, and `<p><img src="rel"><a href="…">click</a> rest</p>` loses its `</a>`, turning the whole paragraph into a third-party link). Keeping the tag name creates no `transformMap` entry; do not fold the drop back into the transform. **Every `<iframe>` is removed** and replaced by a labelled link, counted as `embedsRemoved`. **The slug is assigned once at insert and never appears in an update patch** (`MUTABLE_FIELDS` in `sync.js` omits it and `updatePatch` refuses one) — the natural `update: { ...post }` would rewrite it and break every inbound link on a Substack title edit. **The content hash is taken after sanitization**, over exactly the values written, so tightening the allowlist re-syncs old rows instead of leaving them frozen at a weaker sanitizer. The module **never deletes a row** (RSS shows only the most recent ~20 posts) and **must never be called from a page render**.
- `node .agent/scripts/verify-substack-sync.mjs` checks that module. It needs no network and no database — `readFeed` returns fixtures from `.agent/fixtures/substack/` and the injected store is an in-memory Map that **counts writes**, so "a second sync is a no-op" is a measurement rather than a claim. It carries the sanitizer's attack battery, including every named 2026 CVE, as a regression check. `feed-hostile.xml` has two items on purpose: item 1 is the scheme/raw-text battery and item 2 is the **shape** battery, built from the tag census of 52 real Substack bodies (`picture`/`source` 84 each, `figure` 177, `div` 562, `span` 500, the `button`/`svg` zoom chrome 116) with **only relative URLs**, because the first version of that fixture carried no `<picture>` at all and that is exactly where the `<source srcset>` hole hid. `feed-single-item.xml` is the one to never break: `fast-xml-parser` returns `channel.item` as a bare object rather than an array when a feed has one item, so a pipeline that only handles arrays passes every three-item fixture and fails on the publication's first real post. `store.js` is the one file the script cannot cover — it is the Prisma adapter behind the seam.
- `node .agent/scripts/verify-blog-posts.mjs` checks `src/lib/blog` the same way and needs nothing either: it builds its synced inputs by running the real `normalizeItem` over the same fixtures, then exercises the merge, the ordering and tiebreaker, adjacency, reading time and `withHeadingIds`. `node .agent/scripts/verify-blog-dom.mjs <baseUrl> <out.json> [--expect <file>] [--only …]` is the "MDX posts did not change" gate: it drives `shot.mjs` over `/blog` and the three MDX posts, captures each page as named sections (`title`, `meta`, `article` innerHTML with emotion `css-*` hashes normalized, `rail`, `toc`, `footer`, `cards`, `metrics`), and with `--expect` diffs against a capture from an **unmodified base branch** and exits 1 on any difference. Capture the baseline from a second, clean worktree — a baseline from your own modified tree proves nothing — and check the gate can go red before trusting it green. Its exit code is its own, not `shot.mjs`'s, so it works on branches that predate #158.
- `DATABASE_URL=… node .agent/scripts/seed-substack-fixture.mjs <fixture.xml>` seeds a throwaway database by running the real sync with the real Prisma store and a fixture instead of the network — that is how a synced post gets onto a rendered page locally. It **refuses to run unless `DATABASE_URL`'s host is localhost** (`--force` to override) because it writes rows and the `.env` in a worktree is not necessarily a throwaway, and it never prints the URL. It is the only script that registers `.agent/scripts/lib/alias-resolver.mjs`, which teaches plain Node the `@/` alias; the shared `esm-resolver.mjs` deliberately does not, because "`@/lib/prisma` cannot be loaded" is part of how the verify scripts prove they touch no database.
